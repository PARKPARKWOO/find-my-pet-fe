# Find My Pet 전체 UI/UX·디자인 시스템 설계

**작성일:** 2026-07-30

**상태:** Stage 0 부분 완료, Stage 1–2 로컬 구현·검증 완료, Stage 3–6 대기 (미배포)

**대상:** `find-my-pet-frontend` 전체 사용자 화면

**제품 기준:** `prd/find-my-pet/requirements.md`, `prd/find-my-pet/category-and-adoption.md`, `animal/docs/superpowers/specs/2026-07-25-fmp-search-collaboration-design.md`

---

## 1. 목적

Find My Pet의 기존 기능을 보존하면서 홈, 카테고리, 목록, 상세, 폼, 자료실, 마이페이지와 앞으로 추가할 수색그룹·팀·지도·알림·채팅을 하나의 일관된 디자인 시스템으로 묶는다.

핵심 목표는 다음과 같다.

1. 긴급한 행동은 빠르게 찾되 화면이 불안이나 공포를 과도하게 조성하지 않는다.
2. 실종·보호·입양이라는 서로 다른 목적을 사용자가 처음부터 구분할 수 있게 한다.
3. 홈과 마이페이지의 주요 처리를 두 번 이내 이동으로 끝낸다.
4. 현재 출시되지 않은 기능은 `준비 중` 또는 단계 상태로 명확히 구분한다.
5. 현재 검색, 필터, 지도, 전단지, 공유, 알림, 광고, SEO 동작을 디자인 변경 때문에 깨뜨리지 않는다.

### 1.1 비목표

- 이 작업에서 보호소 전용 API나 입양 게시판 API를 새로 정의하지 않는다.
- `feat/search-group` 백엔드 브랜치를 주 브랜치에 머지하거나 배포하지 않는다.
- 제품 내 통합 지도와 그룹 채팅을 현재 사용할 수 있는 기능처럼 노출하지 않는다.
- 플랫폼 관리자 역할을 수색그룹이나 팀의 제품 역할로 추가하지 않는다.
- 운영 수치, 구조 성공률, 참여자 수 같은 근거 없는 사회적 증거를 만들지 않는다.

## 2. 현재 사실과 기능 단계

### 2.1 현재 코드와 로컬 작업트리에 존재하는 기능

- 홈 통합 검색과 실종·보호 동물 목록
- `/lost`, `/abandonment` 독립 목록 인덱스의 로컬 작업트리 구현
- 실종 소식 상세, 수정·삭제, 상태 변경, 즐겨찾기, 목격 제보
- 실종 위치·탐색 반경·목격·전단지 위치 지도
- 실종 전단지 제작·인쇄/PDF
- 보호 동물 목록·상세·지역 필터
- 카카오톡 공유, Web Share, 링크 복사, 당근 공유 문구
- 알림 목록·읽음 처리와 헤더의 미확인 알림 polling
- 프로필, 내가 등록한 소식, 회원 탈퇴 2단계 흐름
- `/guide`, `/faq`, `/posts` 자료실 콘텐츠

`/lost`, `/abandonment`, 목적 카테고리 레지스트리와 일부 계정 기능은 현재 로컬 커밋에만 있으며 `origin/main`과 운영 배포에는 반영되지 않았다. 이 절은 운영 출시 목록이 아니며, 설계와 구현에서 이를 배포 완료 사실로 표현하지 않는다.

### 2.2 기능 브랜치에만 있는 계약

`feat/search-group`에는 수색그룹·팀·구조화 알림 API가 있으나 주 브랜치 미머지이며 프론트 연결도 없다.

- `SEARCHING` 실종 소식 1개당 수색그룹 1개
- 개인 직접 참여와 지속형 팀 참여
- `OPEN`과 `APPROVAL_REQUIRED` 참여 정책
- 보호자·참여자·팀장·팀원 권한
- 참여 신청·승인·거절·내보내기·차단
- 팀 한 개가 여러 수색그룹을 지원하는 M:N 연결
- 수색 종료와 팀 지원 종료

### 2.3 향후 단계

- Phase 2: 권한 있는 활성 실종 소식과 목격을 모은 개인·팀·그룹 통합 지도
- Phase 3: 수색그룹당 기록형 대화방 한 개
- `/shelters`, `/adoption/wanted`, `/adoption/offer`: 별도 백엔드 계약과 정책 검토 후 구현

### 2.4 2026-08-01 구현 상태

- Stage 0은 부분 완료다. 구현 전 홈·목록·상세·등록·마이페이지 전체의 데스크톱·모바일 캡처는 브라우저 런타임 부재로 남기지 못했다.
- Stage 1의 semantic token, Tailwind mapping, 공통 shell·primitive 호환 layer를 로컬 프론트에 적용했다.
- Stage 2의 전역 내비게이션·Footer, Hero, 목적 카테고리, 상황별 안내, 통합 검색, 실제 공개 API 기반 marquee, opt-in 주변 지도·목록을 로컬 프론트에 적용했다.
- 구현 후 홈은 1440px·390px 스크린샷과 1024px·768px 수동 검토를 남겼다. 자동 브라우저 검증은 Chromium 한 종류에서 수행했다.
- 코드 기준점은 로컬 프론트 `9ac0ddf`이며 `origin/main` 반영과 운영 배포는 확인하지 않았다.
- Stage 3–6의 기존 목록·상세·폼·자료실·마이페이지 전면 이전과 수색그룹·팀·통합 지도·채팅 연결은 아직 시작하지 않았다.

## 3. 확정된 정보 구조와 이름

### 3.1 목적 카테고리

| 이름 | 경로 | 디자인 상태 |
|---|---|---|
| 집을 잃었어요 | `/lost` | 이용 가능 |
| 보호소에서 가족을 기다려요 | `/abandonment` | 이용 가능 |
| 우리집 근처 보호소 | `/shelters` | 준비 중, 비링크 |
| 반려동물을 입양하고 싶어요 | `/adoption/wanted` | 준비 중, 비링크 |
| 반려동물의 새 가족을 찾아요 | `/adoption/offer` | 준비 중, 비링크 |

이름은 화면 크기 때문에 축약하거나 다른 문구로 바꾸지 않는다. 다섯 목적은 후기용 DB `Category`와 무관한 프론트 고정 레지스트리다.

### 3.2 사용자 문구

| 시스템 개념 | 사용자 문구 |
|---|---|
| Lost post / notice | 실종 소식 |
| Search group | 수색그룹 |
| Owner | 보호자 |
| Participant | 참여자 |
| Team leader | 팀장 |
| Team member | 팀원 |
| Admin | 사용하지 않음 |
| Managed searches | 함께 찾는 반려동물 |
| Pending actions | 확인할 요청 |
| Close search | 수색 종료 |
| Team withdrawal | 우리 팀의 지원 종료 |

보호자가 팀 연결을 제거하는 행동은 구현 단계에서 `팀 지원 연결 해제`를 기본 문구로 쓰고, 사용자 검토에서 최종 확정한다.

## 4. 시각 방향

### 4.1 시각적 명제

> 긴급함은 선명하게, 돌봄은 따뜻하게.

행동·상태·권한은 짧고 직접적인 UI로 표현한다. 따뜻한 색, 여백, 문장과 에디토리얼 타이포그래피는 신뢰를 만드는 층으로 쓰되 탐색을 방해하지 않는다.

### 4.2 색상 토큰

| 토큰 | 값 | 용도 |
|---|---|---|
| `canvas` | `#E9E6DF` | 외부 배경 |
| `paper` | `#F5F0E8` | 기본 페이지 배경 |
| `raised` | `#FFFDF8` | 카드·입력·떠 있는 표면 |
| `ink` | `#202A26` | 기본 텍스트·강한 CTA |
| `forest` | `#2F5A49` | 기본 행동·완료·안전 |
| `clay` | `#D66F54` | 실종 신호·주의가 필요한 행동 |
| `wine` | `#704541` | 이야기·에디토리얼 강조 |
| `sighting` | `#4B7FA3` | 목격 위치와 상태 |
| `waiting` | `#B9893B` | 승인 대기 |
| `kakao` | `#FEE500` | 카카오 브랜드 버튼 전용 |

실종 위치는 붉은 계열, 목격 위치는 푸른 계열로 분리한다. 목격을 현재 위치처럼 표현하지 않는다. 전단지 인쇄 팔레트, 카카오 노랑, 지도 상태색은 일반 `primary`에 흡수하지 않는다.

### 4.3 타이포그래피

- 감성적 제목: `Noto Serif KR` 계열
- 기능·본문·폼: Geist 계열 산세리프와 한국어 시스템 fallback
- 본문 기준: 16px / line-height 1.6 이상
- 네비게이션의 크기·높이·간격은 통합안 G의 기본 구조를 유지한다.
- 네비게이션 기본 메뉴 색상만 기존 회색에서 `ink`로 높인다.
- 현재 위치와 hover/focus 상태는 `forest`를 사용하되 구조나 높이를 바꾸지 않는다.

폰트 변경은 줄바꿈과 전단지 레이아웃에 영향을 줄 수 있으므로 전단지 인쇄 영역은 별도로 회귀 검증한다.
폰트를 번들에 추가하면 원본 URL, 라이선스, subset 방법을 provenance 기록에 남긴다. 이번 범위는 따뜻한 light mode 하나이며, 현재 도달하지 않는 dark token을 실제 다크 모드처럼 활성화하지 않는다.

### 4.4 형태와 그림자

- 기본 radius: 12px
- 큰 표면: 16~20px
- pill: 상태·짧은 필터·브랜드 행동에만 사용
- 그림자는 작은 표면에 1단계만 사용하며 움직이는 카드에는 무거운 blur를 적용하지 않는다.
- 차가운 SaaS형 흰색·파랑 조합과 과도한 bento 카드 분할을 피한다.

### 4.5 핵심 시각 구성

홈의 핵심 시각은 장식용 3D나 일반 스톡 이미지가 아니라 다음 세 기능의 조합이다.

1. 왼쪽의 감성 문장과 목적 카테고리
2. 오른쪽의 상황별 반려동물 안내 허브
3. 아래의 실제 최신 데이터 흐름과 지역 지도

이 구성이 제품 기능 자체를 보여주는 focal visual이므로 Three.js는 사용하지 않는다. 기존 Freepik 배너는 홈 핵심 자산에서 제외한다. 향후 사진을 추가하면 출처·라이선스·생성 도구를 코드 근처 manifest에 기록한다.

## 5. 전역 네비게이션

### 5.1 데스크톱

통합안 G의 한 줄 구조를 유지한다.

- 왼쪽: `Find My Pet`
- 중앙: 함께 찾기 / 보호 동물 / 보호소·입양 / 이용 안내
- 오른쪽: 알림 / 마이페이지 / 소식 등록

카테고리 레일이나 2단 헤더를 추가하지 않는다. 사용자 피드백에 따라 레이아웃을 키우지 않고 글씨색 대비만 높인다.
이 네 항목은 여러 화면을 묶는 전역 탐색 label이며, 3.1의 확정 목적 카테고리명을 대체하거나 축약한 카드명이 아니다.

### 5.2 모바일

- 로고와 주요 행동만 상단에 유지한다.
- 메뉴 열림 화면에서 목적과 이용 안내를 한 단계로 보여준다.
- 메뉴 항목과 버튼은 최소 44px 터치 영역을 가진다.
- `button` 안에 `a`를 중첩하지 않고 하나의 적절한 interactive element만 사용한다.

### 5.3 알림과 인증

- 기존 HttpOnly cookie 인증과 `/user/me` 확인 흐름을 유지한다.
- 알림 polling 30초, 최근 5개 popover, `99+`, 전체 보기 동작을 유지한다.
- 알림 항목은 키보드로 접근 가능한 링크 또는 버튼으로 바꾼다.

## 6. 홈 화면

### 6.1 최종 순서

1. 전역 네비게이션
2. Hero: 목적 카테고리 + 상황별 안내
3. 통합 검색
4. 새로 이어지는 소식 marquee
5. 가까운 곳의 지도·제보·그룹 소개
6. 기존 정적 목록과 필터
7. 안전 안내·자료실 연결
8. Footer

별도 `무엇을 도와드릴까요?` 카테고리 섹션은 제거한다. Hero 안에 이미 있는 목적 카테고리와 중복되기 때문이다.

### 6.2 Hero 왼쪽

제목은 `다시 만나는 길을, 동네와 함께.`를 사용한다.

제목 바로 아래에 이용 가능한 두 목적을 큰 행동 카드로 둔다.

- `집을 잃었어요`
- `보호소에서 가족을 기다려요`

준비 중인 세 목적은 큰 카드로 반복하지 않고 같은 영역 아래 작은 비링크 항목으로 표시한다.

### 6.3 Hero 오른쪽: 상황별 반려동물 안내

사용자 화면에 `FAQ`라는 이름을 노출하지 않는다. 섹션 이름은 `상황별 반려동물 안내`를 기본으로 한다.

대표 문구:

> 처음이라 막막할 때, 상황에 맞는 순서를 알려드려요.

우선 노출 항목:

1. 반려동물을 잃어버렸을 때 주변 수색부터 신고·전단지까지 먼저 할 일
2. 보호소에서 내 아이를 확인하고 안전하게 데려오는 방법
3. 보호소 상담·교육·입양 신청 과정
4. 산책과 생활 환경에서 실종을 예방하는 방법

현재 연결 가능한 출처:

- `/guide`: 반려동물 실종 시 단계별 대처
- `/faq`: 보호소 확인·반환·입양 절차·동물등록 제도
- `/posts/dog-missing-guide`
- `/posts/dog-escape-while-walking`
- `/posts/cat-escape-reasons-and-solutions`

`/faq` 경로와 FAQPage 구조화 데이터는 SEO·기존 링크 호환을 위해 유지한다. 홈과 전역 내비게이션의 사용자 노출 문구만 자연어 안내로 바꾼다. 구현 시 안정적인 anchor ID 또는 작은 `featuredGuides` 레지스트리를 만들어 홈 링크가 질문 순서에 의존하지 않게 한다.

### 6.4 검색

Hero 아래의 현재 검색 위치를 유지한다.

- 검색어, 지역, 동물 유형 정규화 동작 유지
- `/search?q=&page=&type=` 계약 유지
- 비어 있는 검색어와 오류 상태를 구분
- 모바일에서 지역 보조 정보는 접되 검색 행동은 유지

### 6.5 새로 이어지는 소식

홈에만 한 줄 marquee를 둔다. 이 영역은 주요 목록을 대체하지 않는 발견용 티저다.

#### 데이터

- `GET /posts`의 최신 `SEARCHING`·`SEEN` 항목
- `GET /abandoned-animals`의 최신 진행 중 보호 동물
- 응답에 실제로 있는 제목, 위치, 시간, 썸네일만 사용
- 예시 이름·장소·시간을 제품 코드에 고정하지 않음

한쪽 API가 실패하면 다른 쪽 데이터만 사용한다. 표시할 데이터가 없으면 marquee 전체를 숨기고 홈 흐름을 유지한다.
원본 카드의 총 너비가 viewport보다 충분히 길지 않으면 반복 애니메이션을 시작하지 않고 정적 목록으로 표시한다.

#### 동작

- 안정적인 카드 폭
- 원본 sequence를 한 번 복제
- `0 → -50%` transform으로 이음새 없는 반복
- 설계 기준 한 바퀴 약 34초, 구현은 트랙 폭을 기준으로 유사한 시각 속도를 유지
- 좌우 edge mask
- hover, `focus-within`, 사용자의 정지 버튼에서 일시정지
- 복제 sequence는 `aria-hidden`이며 focus 대상에서 제외
- 카드 클릭은 공개 상세로 이동
- `prefers-reduced-motion`에서는 애니메이션을 없애고 원본 sequence만 정적 가로 목록으로 표시
- JavaScript가 없어도 원본 항목이 읽히는 정적 fallback 제공

고유하고 반드시 읽어야 하는 상태 변경, 승인 요청, 안전 경고는 marquee에 넣지 않는다.

### 6.6 지도·정적 목록

marquee 아래에서 가까운 공개 실종·목격 위치를 opt-in 지도와 정적 목록으로 이어 보여주고, 보호 동물은 아래 기존 통합 피드에서 계속 제공한다.

- marquee와 별개로 전체 목록·페이지네이션·필터 유지
- 지도 데이터는 현재 공개 범위만 사용
- 향후 통합 지도는 권한 필터가 구현된 뒤 마이페이지와 그룹 화면에 연결
- 팀원 현재 위치나 이동 동선을 수집하지 않음

Stage 2의 홈 지도는 사용자가 `내 위치로 가까운 소식 보기`를 누른 뒤에만 브라우저 위치를 요청하고, 기본 3km와 1·3·5·10km 반경으로 공개 `/posts/nearby`의 `SEARCHING | SEEN` 위치만 조회한다. 프론트는 좌표를 브라우저 저장소에 보관하지 않으며 서버·인프라 보관 여부는 별도 확인 대상으로 남긴다. 카카오 지도 키가 없거나 SDK 로드가 실패해도 같은 결과를 정적 목록으로 제공한다. 그룹 참여자 수, 팀 지원 상태, 비공개 목격 정보는 `feat/search-group` merge와 권한 API 연결 전에는 표시하지 않는다.

## 7. 마이페이지

마이페이지는 기존 프로필·작성 목록에 기능을 덧붙이는 긴 메뉴가 아니라 통합 수색 허브로 확장한다.

### 7.1 첫 화면 전환 항목

- 함께 찾는 반려동물
- 내 팀
- 확인할 요청
- 알림
- 내가 등록한 소식

중첩 사이드바를 만들지 않는다. 데스크톱에서는 같은 화면의 상단 전환, 모바일에서는 짧은 탭 또는 섹션 점프로 처리한다.

### 7.2 함께 찾는 반려동물

- 보호자로 참여
- 개인으로 직접 참여
- 팀을 통해 참여

세 경로를 상태 label로 구분한다. 같은 사람이 직접·팀 경로로 중복돼도 카드와 알림 수를 중복 표시하지 않는다.

### 7.3 통합 지도

- 권한이 있는 활성 실종 소식과 목격만 표시
- 내가 등록 / 직접 참여 / 팀으로 참여 필터
- 실종 지점과 목격 지점의 색상 분리
- 수색 종료 후 읽기 전용 기록으로 이동
- 팀원 위치·동선은 표시하지 않음

통합 지도 API가 준비되기 전에는 활성 기능처럼 렌더링하지 않는다.

### 7.4 확인할 요청

- 직접 참여 승인·거절
- 팀 지원 제안 수락·거절
- 팀 가입 승인·거절

한 화면에서 주요 처리를 끝낸다. 중복 클릭은 서버의 멱등 계약을 이용하고 처리 중·성공·오류 상태를 명시한다.

### 7.5 기존 기능 보존

- `/posts/mine` 작성 목록
- `SEARCHING ↔ FOUND` 상태 변경
- 프로필 정보
- 회원 탈퇴 preview → FMP 데이터 파기 → Auth 탈퇴 순서
- 부분 성공 시 재시도 흐름

회원 탈퇴는 화면 맨 아래 낮은 위계의 별도 영역으로 유지한다.

## 8. 수색그룹·팀·알림·채팅의 화면 원칙

### 8.1 등록

`SEARCHING`을 등록할 때만 참여 방식을 같이 선택한다.

- `자유롭게 참여`가 기본값
- `승인 후 참여` 선택 가능
- `SEEN`과 `FOUND` 등록에는 수색그룹 없음

### 8.2 권한

- 보호자: 글 수정·삭제, 참여 처리, 차단, 팀 지원 처리, 전체 수색 종료
- 참여자: 자신의 직접 참여 종료
- 팀장: 팀 멤버십과 지원 관리, 우리 팀의 지원 종료
- 팀원: 활성 팀 지원을 통한 참여
- 팀장이나 팀원은 전체 수색 종료 불가

### 8.3 종료

보호자가 `수색 종료`를 실행하면 실종 소식은 `FOUND`, 그룹은 읽기 전용 `ARCHIVED`가 된다. 재활성화 동작을 제공하지 않는다.

팀장은 `우리 팀의 지원 종료`만 수행한다. 종료·삭제·권한 회수 후 신규 알림 fan-out과 채팅 쓰기는 중단한다.

### 8.4 카카오톡 공유

- 공개 `/lost/{postId}` 링크 공유
- 그룹 비밀 초대 링크가 아님
- SDK 실패 시 링크 복사
- 로그인 후 원래 실종 소식으로 복귀
- 공유 계측은 기존 개인정보 비저장 계약 유지

### 8.5 채팅

Phase 3에서 그룹당 기록형 방 한 개만 둔다.

- 텍스트만
- 팀 전용 하위 방 없음
- 종료 후 읽기 전용
- 권한 회수 즉시 조회·구독 차단
- 현재는 외부 카카오 오픈채팅 URL이 유일하므로 제품 내 채팅 UI를 활성 표시하지 않음

## 9. 디자인 시스템 구현 구조

### 9.1 토큰

기존 `globals.css`의 shadcn 계열 CSS 변수를 제거하지 않고 새 semantic token을 매핑한다.

- surface: canvas / paper / raised / inverse
- text: primary / secondary / muted / inverse
- action: primary / secondary / destructive / brand
- state: searching / sighting / found / protected / waiting / archived
- map: missing-pin / sighting-pin / radius / selected
- radius, spacing, container, shadow, typography scale

Tailwind class를 문자열 결합으로 만들지 않고 variant map이나 `cva`를 사용한다. 현재 `xs: 480px` breakpoint는 유지한다.

### 9.2 primitive 통합

현재 `src/components/ui`와 `src/app/_components/ui`의 Button 계약이 다르므로 import를 한 번에 치환하지 않는다.

1. `src/components/ui`를 장기 표준으로 지정
2. 기존 경로에 adapter/re-export 유지
3. 기존 사용처의 `size`와 `variant`를 먼저 명시
4. 화면별로 이전
5. 모든 사용처가 이동한 뒤에만 legacy primitive 제거

우선 추가할 공통 패턴:

- `PageShell`
- `Container`
- `SectionHeading`
- `PurposeCard`
- `GuideLinkCard`
- `PetCard`
- `FilterChip`
- `StatusBadge`
- `StatusBanner`
- `EmptyState`
- `ErrorState`
- `InfoCard`
- `ActivityHub`
- `RequestQueue`
- `MarqueeRail`

### 9.3 아이콘

새로운 인터페이스 아이콘은 Solar 계열을 Iconify로 사용한다. 텍스트로 충분한 곳에는 아이콘을 추가하지 않는다. 카카오 브랜드 심볼은 브랜드 자산 규칙을 따른다.

## 10. 모션 시스템

### 10.1 도구 결정

- GSAP: 주요 등장·marquee·ScrollTrigger 모션
- Lenis: 유일한 smooth-scroll 엔진
- Locomotive Scroll: 사용하지 않음
- Three.js: 사용하지 않음

Lenis를 선택한 이유는 GSAP과 결합이 단순하고 DOM 구조를 크게 바꾸지 않아 Next.js, Kakao 지도, 폼과 충돌 위험이 Locomotive보다 낮기 때문이다.

Lenis는 홈·카테고리 같은 발견 화면에만 활성화한다. 폼, 지도, 목록, 마이페이지, 법률·전단지 화면은 native scroll opt-out으로 둔다. 다른 smooth-scroll 엔진을 병행하지 않는다.

### 10.2 모션 규칙

- 콘텐츠는 애니메이션 전에도 읽을 수 있어야 함
- Hero는 짧은 opacity/translate 등장
- 섹션 reveal은 12~20px 이내
- scroll-scrub은 정보 이해에 필요할 때만 사용
- marquee 외의 무한 장식 반복 금지
- hover/focus에서 중요한 움직임 정지
- `prefers-reduced-motion`에서 Lenis와 scrub을 끄고 최종 상태 즉시 표시
- JavaScript 미실행 시 모든 핵심 콘텐츠와 링크가 정적으로 표시

## 12. 단계적 적용 순서

### Stage 0 — 기준선

**상태: 부분 완료.** 실행 기준선과 dirty-worktree 경계는 기록했지만, 구현 전 전체 경로의 데스크톱·모바일 캡처는 남기지 못했다.

- 기존 dirty worktree 보존
- 홈, 목록, 상세, 등록, 마이페이지의 데스크톱·모바일 기준 캡처
- lint, type-check, build, category contract 현재 결과 기록

### Stage 1 — 토큰과 호환 layer

**상태: 로컬 구현·검증 완료, 미배포.**

- semantic CSS variables
- Tailwind token mapping
- primitive adapter
- container·typography·focus·reduced motion 기본값

### Stage 2 — 전역 셸과 홈

**상태: 로컬 구현·검증 완료, 미배포.**

- Navigation / Footer
- 최종 Hero 구조
- 상황별 안내 registry
- 검색
- 실제 API 기반 marquee
- 목적 카테고리 중복 제거

### Stage 3 — 현재 카테고리·목록·상세

**상태: 대기.** 기존 기능은 유지되지만 전체 디자인 시스템 이전 범위는 미구현이다.

- `/lost`, `/abandonment`, `/search`
- 카드·필터·페이지네이션
- 상세·공유·상태·빈 화면·오류 화면
- 지역 보호 동물 허브

### Stage 4 — 폼·지도·자료실

**상태: 대기.**

- `/register`, `/edit/[id]`
- 지도 패널
- `/guide`, `/faq`, `/posts`
- 자료실 사용자 문구 통합
- 전단지 인쇄 회귀

### Stage 5 — 마이페이지·알림

**상태: 대기.**

- 프로필과 기존 작성 목록 이전
- ActivityHub shell
- 알림 키보드 접근성
- 탈퇴 흐름 회귀

### Stage 6 — 신규 기능 연결

**상태: 대기.**

백엔드 주 브랜치 merge와 API 계약 확인 후에만 그룹·팀·승인 요청 화면을 활성화한다. 통합 지도와 채팅은 각각 Phase 2/3에서 별도 기능 계획과 테스트를 거친다.

## 13. 접근성·성능·검증

### 13.1 접근성

- keyboard focus-visible
- 최소 44px 터치 영역
- 링크·버튼 semantic 분리
- 준비 중 목적은 비링크와 명시적 상태

- 대비 검증: 기본 텍스트, 상태 badge, 버튼, 지도 marker

### 13.2 성능

- Server Component를 기본으로 유지
- marquee와 지도만 작은 client island
- 움직이는 카드의 heavy shadow/filter 금지

- Next Image 계약 유지
- Lenis와 GSAP은 적용 페이지에서만 로드

### 13.3 테스트

각 Stage에서 다음을 실행한다.

- lint
- type-check
- production build
- category contract 9개
- 새 design registry·link semantics·marquee focus 계약 테스트
- 데스크톱/모바일 시각 비교
- keyboard-only 탐색
- reduced-motion

1. 확정 카테고리명 다섯 개가 정확히 사용된다.
2. Hero의 활성 카테고리와 별도 카테고리 섹션이 중복되지 않는다.
3. 상황별 안내는 `FAQ`라는 사용자 문구 없이 현재 자료실로 연결된다.
4. marquee는 실제 API 데이터만 사용하고 정지·축소 모션·정적 fallback을 제공한다.
5. 마이페이지의 기존 프로필·내 글·탈퇴 기능이 유지된다.
6. 준비 중 기능을 클릭 가능한 출시 기능처럼 표현하지 않는다.
7. 검색·필터 URL·공유 fallback·지도·전단지·SEO 계약이 유지된다.
8. 네비게이션은 원래 한 줄 구조를 유지하고 색상 대비만 개선한다.
9. semantic token과 adapter를 통해 화면별로 안전하게 이전할 수 있다.
10. lint, type-check, production build와 관련 계약 테스트가 통과한다.
